1. Executive Summary & Mission Scope

This project demonstrates an enterprise private multi-VPC networking pattern in AWS without exposing private workloads to the public internet or utilizing expensive NAT Gateways. Workload A resides in an isolated private subnet inside VPC A (10.10.0.0/16) and Workload B resides in an isolated private subnet inside VPC B (10.20.0.0/16).

By establishing an AWS VPC Peering Connection (ewb-a-b-peer), configuring bidirectional custom route table entries, setting stateful least-privilege security groups, and implementing an OpenSSH ProxyJump Bastion Host in VPC A's public subnet, bidirectional private communication was established and rigorously proven.

6. Keyless Administrative Access: SSH ProxyJump

Security best practice mandates that the private key ewb-lab.pem is never uploaded or copied to the intermediary bastion host. OpenSSH's ProxyJump creates an encrypted tunnel through the bastion directly to the target instance while authenticating locally from the student machine. 

# Configuration inside ~/.ssh/config:
Host ewb-bastion
    HostName 13.234.120.45
    User ec2-user
    IdentityFile ~/.ssh/ewb-lab.pem
    IdentitiesOnly yes

Host ewb-app-a
    HostName 10.10.2.10
    User ec2-user
    IdentityFile ~/.ssh/ewb-lab.pem
    IdentitiesOnly yes
    ProxyJump ewb-bastion

Host ewb-app-b
    HostName 10.20.1.10
    User ec2-user
    IdentityFile ~/.ssh/ewb-lab.pem
    IdentitiesOnly yes
    ProxyJump ewb-bastion

9. Viva Voce & Conceptual Defense (Workbook Page 12)

Q1: Why is the return route needed?

Answer: IP routing is intrinsically hop-by-hop and asymmetric. While the forward route in ewb-rt-a-private successfully directs the packet destined for 10.20.1.10 into the peering connection pcx-ID, the return packet generated by App-B (ICMP Echo Reply or TCP SYN-ACK) has a destination address of 10.10.2.10. App-B's subnet route table (ewb-rt-b-private) must contain an explicit route pointing 10.10.0.0/16 back to pcx-ID. Without this return route, VPC B has no forwarding rule for destination 10.10.2.10 and drops the packet.

Q2: Why is the App-B SSH source the bastion private IP?

Answer: OpenSSH ProxyJump instructs the client's local SSH daemon to establish an SSH session with the bastion host and request a TCP port forward to 10.20.1.10:22. The bastion's SSH daemon opens a brand-new TCP socket originating from its own primary private network interface (10.10.1.10). Consequently, the TCP SYN packet arriving at App-B's network interface carries 10.10.1.10 as the source IP, requiring App-B's security group to whitelist 10.10.1.10/32 rather than the client's laptop public IP.

Q3: Why does Active peering not guarantee a successful ping?

Answer: An "Active" peering connection represents only layer-3 connectivity between VPC network fabrics. Successful communication requires a three-tier convergence: (1) Route Tables on both sides must contain explicit destination CIDRs pointing to the peering ID; (2) Security Groups must explicitly allow inbound ICMP Echo Request (Type 8, Code 0); (3) Network ACLs (NACLs) must allow inbound and outbound traffic. Active peering without route entries or SG ingress rules results in complete packet loss.

Q4: Can VPC B use VPC A's internet gateway over peering?

Answer: No. AWS VPC Peering is non-transitive and expressly prohibits edge-to-edge routing. An Internet Gateway attached to VPC A cannot be used by instances in VPC B across a peering connection (known as transitive routing). If VPC B requires internet access, it must deploy its own Internet Gateway / NAT Gateway, or use AWS Transit Gateway with centralized egress routing.
