Workbook Page 12 - Viva Voce & Technical Defense

1. Why is the return route needed?

IP routing is asymmetric and hop-by-hop. Forward packets from App-A arrive at App-B via pcx-ID. When App-B crafts a response, its destination is 10.10.2.10. App-B's route table (ewb-rt-b-private) must contain an explicit route pointing 10.10.0.0/16 back to pcx-ID; without it, VPC B drops the reply packet.

2. Why is the App-B SSH source the bastion private IP?

OpenSSH ProxyJump instructs the bastion host's SSH daemon to open a new local TCP socket originating from 10.10.1.10 directly to 10.20.1.10:22. Therefore, the SYN packet reaching App-B carries the bastion private IP, not the laptop public IP.

3. Why does Active peering not guarantee a successful ping?

Active peering only establishes the layer-3 virtual link. Packets will still be dropped unless (a) Subnet route tables target the peering connection ID, (b) Instance Security Groups explicitly allow inbound ICMP Echo Request, and (c) Stateless NACLs permit the traffic.

4. Can VPC B use VPC A's internet gateway over peering?

No. AWS VPC Peering is non-transitive and expressly blocks edge-to-edge routing. Traffic cannot enter VPC A through an Internet Gateway and cross peering into VPC B. VPC B requires its own IGW/NAT or an AWS Transit Gateway.

Workbook Page 14 - Teardown Order

  1. Terminate EC2 instances: ewb-bastion, ewb-app-a, ewb-app-b. Verify EBS root volumes are deleted.
  2. Delete VPC Peering Connection: ewb-a-b-peer.
  3. Delete custom security groups: ewb-sg-bastion, ewb-sg-app-a, ewb-sg-app-b.
  4. Disassociate and delete custom route tables and subnets.
  5. Detach and delete Internet Gateway: ewb-igw-a.
  6. Delete VPCs: ewb-vpc-a, ewb-vpc-b.
